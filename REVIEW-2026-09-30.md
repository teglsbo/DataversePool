## Executive summary

1. **The throttle detector is probably inert on the default transport.** It matches only
   `HttpOperationException` (Web API path); SOAP-path 429s arrive as
   `FaultException<OrganizationServiceFault>` and are never recognised. Fix this before
   implementing ADR-0024 — otherwise its `throttled` outcome and `retry_after` histogram read zero
   forever.
2. **The ADRs' SDK survey missed `RecommendedDegreesOfParallelism`,** a public, read-only property
   fed by the `x-ms-dop-hint` response header on *both* transports. ADR-0006 and ADR-0016 both name
   `x-ms-dop-hint` as out of reach. It isn't. Cheapest telemetry win in the repo.
3. **`x-ms-ratelimit-*` really is unreachable through `ServiceClient`** — ADR-0008's conclusion
   holds, confirmed against the assemblies.
4. Three correctness bugs with production impact: an unguarded policy callback that permanently
   leaks pool capacity, an incomplete return-scrub that lets a caller defeat ADR-0016, and a Polly
   adapter that marks a throttled client unhealthy in direct contradiction of ADR-0008.

# Part 1 — General assessment

## Architecture and layering

The layering is clean and honest to its own ADRs. `ConnectionPool.Core` is genuinely domain-free
(no SDK reference in `src/ConnectionPool.Core/ConnectionPool.Core.csproj`), all Dataverse knowledge
lives in `IPooledResourcePolicy<T>` implementations (`src/ConnectionPool.Core/IPooledResourcePolicy.cs`),
and both optional packages (`Metrics`, `Polly`) depend only on Core.

The ADR trail is unusually good; most non-obvious decisions are traceable. That said, the ADR set
reads as a log of review rounds rather than a design record — ADR-0011/0012/0013/0014/0022 are each
"fixes found in review round N" and several supersede each other's details, so answering "what is
the current behaviour" requires reading five documents. ADR-0015 acknowledged this and paused it.

## Core pool soundness (`ResourcePool`, `Slot`, `PooledLease`)

The capacity/creation gate model is sound: `_capacityGate` bounds leased+creating, idle slots carry
no permit, and creation is serialised (`src/ConnectionPool.Core/ResourcePool.cs:19-33`). The
AcquireTimeout linked-CTS design (`ResourcePool.cs:147-152, 228-233`) and the
cancellation-vs-CreateTimeout disambiguation (`ResourcePool.Recycling.cs:116-139`) are correct.

Specific concerns:

### 1. Unguarded policy callback on the return path — permanent capacity leak ✓ verified

`ReturnAsync` calls `_policy.OnReturned(slot.Resource!)` *before* pushing the slot and releasing the
permit (`src/ConnectionPool.Core/ResourcePool.cs:286-288`):

```csharp
slot.State = SlotState.Idle;
slot.BecameIdleAt = DateTimeOffset.UtcNow;
_policy.OnReturned(slot.Resource!); // scrub any per-lease state before next caller (ADR-0009)
_idle.Push(slot);
_capacityGate.Release();
```

Every other policy call is wrapped (`SafeDisposeAsync`, `ResourcePool.Recycling.cs:184-199`); this
one is not. If `OnReturned` throws, the slot is lost **and** the capacity permit is never released —
a silent, permanent capacity leak, one slot per occurrence. For the Dataverse policy this means an
exception from `ServiceClient.CallerId`'s setter (e.g. a clone whose `ConnectionService` was torn
down) wedges a slot for the life of the process.

**Fix:** wrap in try/catch and either mark the slot unhealthy and recycle, or release the permit in
a `finally`.

### 2. Background-recycle vs. shutdown race

`RecycleInBackgroundAsync` checks `_poolDisposed`, then pushes to `_idle`
(`ResourcePool.Recycling.cs:69-79`). `DisposeAsync` can set the flag and drain `_idle` between those
two lines (`ResourcePool.cs:376, 400-403`); the recycled resource is then pushed into a stack nobody
drains and is never disposed. ADR-0022 fixed a *different* ordering issue (permits released before
drain); this one is not covered, and `DisposeAsync` never awaits in-flight recycles at all.

### 3. Shutdown latency is unbounded in practice

`DisposeAsync` waits up to 5s *per permit*, sequentially (`ResourcePool.cs:384-395`). With
`MaxSize=32` and leases trickling back, that is up to ~160s of `StopAsync`.

### 4. `PoolStats.LeasedCount` is derived, not tracked

`ResourcePool.cs:245` computes it as `created - idle`, so it includes slots mid-recycle and slots
permanently lost to leaks. The metrics gauge describes it as "Resources currently leased out to a
caller" (`src/ConnectionPool.Metrics/PoolMetrics.cs:85`) — inaccurate. `LeastConnectionsSlotSelectionStrategy`
steers on this value.

### 5. `ConsecutiveOperationalFailures` is pool-wide, not per-slot ✓ verified

It is reset by *any* healthy return from *any* slot (`ResourcePool.cs:283`). Under mixed load, a
member with one persistently broken clone and seven healthy ones never reaches the breaker
threshold. `TODO.md:361` acknowledges this; it should also be stated in
`HealthAwareRoundRobinSlotSelectionStrategy`'s docs, which currently promise it "skips members whose
underlying pool is persistently failing".

### 6. Minor

`CreateThroughGateAsync` races `Task.Delay(timeout, ct)` against creation and never cancels the
delay when creation wins (`ResourcePool.Recycling.cs:109`) — harmless, but leaves a timer alive per
create for the full `CreateTimeout`.

The `MarkUnhealthy`-after-`DisposeAsync` TOCTOU (`src/ConnectionPool.Core/PooledLease.cs:37-55`) is
documented in ADR-0003/0007 and acceptable for a contract-based design.

## Circuit breaker and strategies

`src/ConnectionPool.Dataverse/MemberCircuitBreaker.cs` is well-reasoned: single-probe half-open,
generation-correlated claims, unused-claim release. Two nits:

- `CompleteProbe`'s failure branch uses `DateTimeOffset.UtcNow` directly
  (`MemberCircuitBreaker.cs:179`) whereas everything else takes `now` as a parameter — the one path
  that can't be tested deterministically.
- `IsEligible` removes state under `!isOpen` (`MemberCircuitBreaker.cs:104-108`), so a member that
  flaps around the threshold gets a fresh `OpenedAt` each time and never accumulates cooldown. Fine,
  but undocumented.

## Public API design

`DataversePool` / `DataverseLease` / `DataverseUserPool` are small and coherent. Problems:

### `PooledOrganizationService` never signals connection health

Its only exception hook is `ReportIfThrottled` (`src/ConnectionPool.Dataverse/PooledOrganizationService.cs:63-72`);
it never calls `MarkUnhealthy`. So for the audience the README explicitly targets — drop-in
`IOrganizationServiceAsync2` consumers (`README.md:461-494`) — `ConsecutiveOperationalFailures` never
increments, the "health-aware" breaker only ever opens on *clone* failures, and a member whose
clones all fail at call time is round-robined forever. `README.md:146-149`'s promise that the default
strategy "circuit-opens a consistently-failing member" does not hold for facade users.

`ExecuteWithThrottleRetryAsync` has the same gap (`src/ConnectionPool.Dataverse/DataversePool.cs:207-236`):
non-throttle failures propagate without any health signal.

### The Polly adapter does the opposite wrong thing ✓ verified

`AddRetryWithPoolHealthSignal` marks the lease unhealthy on *every* retried exception
(`src/ConnectionPool.Dataverse.Polly/PollyPoolHealthSignalExtensions.cs:47-50`), including a 429:

```csharp
if (args.Outcome.Exception is { } exception)
{
    lease.MarkUnhealthy(exception);
}
```

The README example uses `Handle<Exception>()` (`README.md:417-423`). A throttled call therefore
disposes and re-clones a perfectly good `ServiceClient` and increments the operational-failure
counter — directly contradicting ADR-0008's principle that throttling must not mark unhealthy, and
capable of circuit-opening a member that is merely over budget.

Separately: binding a Polly v8 pipeline to a single `PooledLease` forces a pipeline build per lease,
against Polly's own reuse guidance.

### Other API notes

- The sync members of `PooledOrganizationService` block with `GetAwaiter().GetResult()`
  (`PooledOrganizationService.cs:128-145`) — documented, but a real deadlock hazard on
  sync-context hosts. Consider `NotSupportedException` behind an opt-in rather than silently blocking.
- `DataverseUserPool.Name` is unvalidated (`src/ConnectionPool.Dataverse/DataverseUserPool.cs:23`),
  yet it is a dictionary key in the breaker and the metric tag ADR-0024 wants to emit.
- `AddDataverseUserPool` offers no way to pass `DataverseClientOptions`
  (`src/ConnectionPool.Dataverse/DataversePoolServiceCollectionExtensions.cs:19-42`), so the README's
  own recommended `MaxRetryCount = 0` is unreachable from the DI path.

## Correctness risks

### CallerId scrubbing is incomplete ✓ verified

`OnReturned` resets `CallerId` and `CallerAADObjectId` only
(`src/ConnectionPool.Dataverse/DataverseServiceClientPolicy.cs:121-125`):

```csharp
public void OnReturned(ServiceClient resource)
{
    resource.CallerId = Guid.Empty;
    resource.CallerAADObjectId = null;
}
```

The SDK probe confirms other public, settable, per-instance state a lease holder can mutate and leak
to the next caller: `SessionTrackingId`, `ForceServerMetadataCacheConsistency`,
`DisableCrossThreadSafeties`, `MaxRetryCount`, `RetryPauseTime`,
`UseExponentialRetryDelayForConcurrencyThrottle`, `UseWebApi`, and — ironically —
`EnableAffinityCookie`, which a caller can flip back to `true` and thereby **defeat ADR-0016 for
that slot permanently**.

**Fix:** re-apply the policy's full baseline on return, not two fields.

### Throttle detection is blind on the default transport

`DataverseThrottleDetector` recognises only `HttpOperationException`
(`src/ConnectionPool.Dataverse/DataverseThrottleDetector.cs:66-76`) ✓ verified. The SDK produces
that type only on the **Web API** transport. On the SOAP/WCF path — which `README.md:151-158` itself
says carries *all reads regardless* of `UseWebApi`, and everything else at the default
`UseWebApi=false` — a 429 surfaces as `FaultException<OrganizationServiceFault>` with error code
`-2147015898` / `-2147015902` / `-2147015903` and `Retry-After` in
`OrganizationServiceFault.ErrorDetails["Retry-After"]`, not in HTTP headers.

The repo's own evidence points at this and the dots were never connected:

- `tests/ConnectionPool.Dataverse.Tests/LiveInsertThroughputBenchmarkTests.cs:200-206` had to add a
  string-match fallback on `Contains("Number of concurrent requests exceeded the limit")` *alongside*
  `TryGetRetryAfter`.
- `README.md:115-116` calls those rejections "faults".
- `TODO.md:338` still lists SOAP-fault detection as "unverified whether this SDK version even throws
  SOAP faults for throttling".

**Consequence:** `ReportIfThrottled`, `ExecuteWithThrottleRetryAsync`, the facade's throttle
reporting, and both strategies' throttle-skipping are effectively inert for the workloads the library
is pitched at. No live test has ever observed a *detector-recognised* 429 through the SDK —
`LiveConcurrencyThrottleTests` saw zero, and the pinned test bypasses the SDK entirely.

ADR-0016's "`MaxRetryCount=0` still leaves `Retry-After` on the exception, by reasoning"
(`docs/adr/0016-affinity-cookie-forced-off-retry-knobs-exposed.md:59-67`;
`src/ConnectionPool.Dataverse/DataverseClientOptions.cs:39-51`) is only true on the Web API path.

> **Caveat:** the SOAP exception shape is inferred from the SDK's structure and the repo's own test
> evidence, not observed live. Confirm against a real tenant before building on it.

### Synchronous network calls inside async

`new ServiceClient(connectionString, logger)` and `baseClient.Clone(_logger)`
(`DataverseServiceClientPolicy.cs:87, 168`) block a thread-pool thread and ignore the
`CancellationToken`.

## Test coverage

Roughly 150 unit tests. Core is well covered (timeouts, shutdown ordering, leak reporting, gate
serialisation). Real gaps:

- No test constructs a `FaultException<OrganizationServiceFault>` for the detector —
  `tests/ConnectionPool.Dataverse.Tests/DataverseThrottleDetectorTests.cs:16-32` only builds
  `HttpOperationException`, so the gap above is invisible to CI.
- No test for the recycle/dispose race (Core §2).
- No stress/interleaving test of `AcquireAsync` / `ReturnAsync` / `MarkUnhealthy`.
- Nothing exercises `OnReturned` against a real client.
- **Live tests "skip" by early `return`** (`tests/ConnectionPool.Dataverse.Tests/LivePinnedWebApiConcurrencyTests.cs:38-45`),
  so they report as *passed* without credentials. Use `Skip` / `SkippableFact` so a green run means
  something.

The live suite is otherwise exemplary in its self-correction (`TODO.md:160-170`).

## Documentation honesty

Mostly good and refreshingly self-critical. Issues:

- `docs/adr/0018-metrics-adapter-observable-gauges.md:9-10` claims "routine `ILogger` logging
  throughout". The library emits **zero** log statements; `ILogger` is only forwarded to the SDK
  (`DataverseServiceClientPolicy.cs:87, 168`).
- `README.md:20` says a clone costs "hundreds of ms to seconds", while ADR-0002:10 measures ~1ms warm
  sequential. The README leans on the cold/contended number to sell pooling.
- The headline "40% more throughput" blockquote (`README.md:26-31`) is the raw-`HttpClient` pinned
  experiment, **not** a library measurement. The library-path result is only "all 160 succeeded",
  with no single-user library baseline.
- ADR-0008/0016/0024's "ServiceClient exposes no hook" is overstated — see Part 2.

# Part 2 — Telemetry and observability

## a) What exists today

**Implemented:**

| Mechanism | Location |
|---|---|
| `PoolStats` — 9 point-in-time fields | `src/ConnectionPool.Core/PoolStats.cs` |
| `HealthChanges` — hand-rolled `IObservable<SlotHealthChanged>`, 5 states | `ResourcePool.cs:253, 423-458` |
| `PoolOptions.OnLeakDetected` — thread-pool dispatched | `ResourcePool.cs:292-335` |
| `PoolAcquireTimeoutException.Stats` | `src/ConnectionPool.Core/PoolAcquireTimeoutException.cs` |
| Per-member `ThrottledUntil` / `IsThrottled` | `src/ConnectionPool.Dataverse/DataverseUserPool.cs:56-66` |
| 9 observable gauges tagged `pool.name` | `src/ConnectionPool.Metrics/PoolMetrics.cs:67-110` |

`PoolMetrics` weaknesses: it calls `statsProvider()` **nine times per collection**, constructs a new
`Meter` per instance rather than accepting `IMeterFactory`, and has no gauge for throttle state,
breaker state, or `RecommendedDegreesOfParallelism`.

**`ILogger`: the library itself logs nothing.**

**Specified but not implemented:** ADR-0024 (operation counters, latency histograms, active/waiting
up-down counters, outcome/retry/`Retry-After` instruments) is **Proposed only** — no `Meter` exists
anywhere in `ConnectionPool.Dataverse` (grep confirms). `TODO.md:364-369` lists it as open.

## b) What Dataverse server-side telemetry is actually reachable

Grounded in the 1.2.27 assemblies.

### The ADR-0008 core claim is correct but incomplete

There is no public callback, event, or property that hands back response headers for `Execute`/CRUD
on success. However, the ADRs' reflection survey missed several public members:

**1. `ServiceClient.RecommendedDegreesOfParallelism` is fed by `x-ms-dop-hint`.** ✓ verified
(`x-ms-dop-hint` and `RecommendedDegreesOfParallelism` both present in the assembly's UTF-16 string
table). Public, read-only, parsed on **both** transports — `DataverseTelemetryBehaviors.AfterReceiveReply`
(SOAP) and `Command_WebExecuteAsync` (Web API). A zero-reflection, per-clone, server-supplied load
hint, updated after every call. **The library never reads it.**
`docs/adr/0006-...:11` and `docs/adr/0016-...:68` both name `x-ms-dop-hint` as out of reach. It is not.

**2. `ExecuteWebRequestAsync` returns the raw `HttpResponseMessage`** with all headers — only for
caller-composed Web API requests, but the live tests already use it (`LiveDataversePoolMultiUserTests`).

**3. Outbound correlation is fully supported:** ✓ verified (`x-ms-client-request-id`,
`x-ms-client-session-id`, `REQ_ID` all present in the assembly).
- `CreateRequestBuilder().WithHeader / WithRequestId / WithCorrelationId`, or
  `request.Parameters["HEADERLIST"]`
- `ConnectionOptions.RequestAdditionalHeadersAsync`
- `OrganizationRequest.RequestId` → `x-ms-client-request-id`
- `ServiceClient.SessionTrackingId` → `x-ms-client-session-id`
- `x-ms-app-session-id` does **not** exist in the SDK.

**4. On failure:** Web API path exceptions carry the full header set in
`HttpOperationException.Response.Headers` (including the ratelimit headers); SOAP faults carry only
`ErrorDetails["Retry-After"]`.

### What the SDK never reads ✓ verified

The strings `x-ms-ratelimit-burst-remaining-xrm-requests`, `x-ms-ratelimit-time-remaining-xrm-requests`,
`x-ms-service-request-id`, and `ARRAffinity` **do not appear anywhere** in
`Microsoft.PowerPlatform.Dataverse.Client.dll`, `Microsoft.Xrm.Sdk.dll`, or
`Microsoft.Crm.Sdk.Proxy.dll` (checked in both 1.2.2 and 1.2.27, UTF-16 string table).

The SDK reads exactly: `Set-Cookie` (into an internal cookie jar), `x-ms-dop-hint`, `Location`, and
`Retry-After`. The rate-limit headers are therefore reachable **only by capturing HTTP responses
yourself**.

### Response-capture routes, in order of supportability

**1. `DiagnosticListener("HttpHandlerDiagnosticListener")` — zero reflection, SDK-agnostic.**
Both transports ultimately use `System.Net.Http.HttpClient` (WCF's `HttpChannelFactory` and the
SDK's internal `IHttpClientFactory` named `"DataverseHttpClientFactory"`). The runtime's
`System.Net.Http.HttpRequestOut.Stop` payload therefore exposes the `HttpResponseMessage` — all
headers, including `Set-Cookie` — for every Dataverse call. Process-global, so filter by environment
host. Bonus: the built-in `System.Net.Http` meter gives per-host request duration/count for free.

**2. `IEndpointBehavior` on `ServiceClient.OrganizationWebProxyClient`** — one internal property,
then public WCF API. `IClientMessageInspector.AfterReceiveReply` gets
`HttpResponseMessageProperty.Headers`. This is exactly how the SDK itself reads `x-ms-dop-hint`.
Covers the SOAP path, i.e. all reads.

**3. Handler injection into the internal `"DataverseHttpClientFactory"`** — via
`ConnectionService.WebApiHttpClient` or `HttpClientFactoryOptions[...].HttpMessageHandlerBuilderActions`
through the internal `ClientServiceProviders.Instance`. Covers the Web API path. Note `Clone` does
**not** copy `WebApiHttpClient`, so this is per-clone work.

### Can the library count distinct frontend servers?

Not from any header designed for it — `x-ms-service-request-id` / `req_id` are per-*request* ids.

The only per-response server-identity signal is the `ARRAffinity` / `ARRAffinitySameSite`
`Set-Cookie` value, an opaque hash of the backend worker. The pinned test already relies on it
(`tests/ConnectionPool.Dataverse.Tests/LivePinnedWebApiConcurrencyTests.cs:86-97, 452-457`) — but only
because it drives raw `HttpClient`. With `EnableAffinityCookie=false` the server still *sends* the
cookie on every response; the SDK just doesn't replay it.

Counting distinct cookie values over a sliding window is therefore a workable **approximation** of
"frontends hit" — but it requires one of the capture routes above and rests on an undocumented
implementation detail Microsoft can change.

### How close to the rate limit?

Only via `x-ms-ratelimit-burst-remaining-xrm-requests` / `-time-remaining-` captured from responses.
Two honest caveats the ADRs already half-state:

- Microsoft labels these **diagnostic**, not a rate-control signal.
- With affinity disabled, each value is *one server's* view, so it jumps around per response.

The **concurrency ceiling** — the limit the library actually hit in every live test — has no header
at all. It is only visible as a 429/fault after the fact. `RecommendedDegreesOfParallelism` is the
only server-supplied *leading* concurrency signal, and it is public.

## c) Recommendations, ranked by cost vs. supportability

### 1. Fix the detector before adding any throttle telemetry
*Trivial · fully supported · blocking prerequisite*

Match `FaultException<OrganizationServiceFault>` on error codes `-2147015898` / `-2147015902` /
`-2147015903` and read `ErrorDetails["Retry-After"]`. `System.ServiceModel.Primitives` is already a
transitive dependency. Add a unit test that constructs that fault, and rerun the insert-overload
probe to confirm `ReportIfThrottled` fires without the string fallback.

Without this, ADR-0024's `throttled` outcome and `retry_after` histogram will read zero in production.

### 2. Publish `RecommendedDegreesOfParallelism` as a per-member gauge
*Trivial · fully supported · zero reflection*

Sample it in `OnReturned` (the policy already touches the client there) into a per-member field, and
expose `dataversepool.member.dop_hint`. While there, add:

- `dataversepool.member.throttled` (0/1)
- `dataversepool.member.throttled_until_seconds`
- `dataversepool.member.breaker_state` (`closed` / `open` / `half_open`)

All of it is in-process state the library already holds. Also move `PoolMetrics` to accept
`IMeterFactory` and snapshot stats **once** per collection instead of nine times.

### 3. Implement ADR-0024 as written
*Low cost · supported*

Plus: set `OrganizationRequest.RequestId` on the facade/helper paths and `SessionTrackingId` per
member at clone time, so every controlled call is correlatable with Dataverse's server-side telemetry
and with a Microsoft support ticket. Add the facade/helper `MarkUnhealthy` signal for non-throttle
SDK failures while in that code.

### 4. Opt-in SDK-agnostic response-observer package
*Medium cost · supported by the runtime, not by the SDK · mark experimental*

A `DiagnosticListener` subscriber filtered to the environment host, extracting `x-ms-ratelimit-*`,
`x-ms-dop-hint`, `x-ms-service-request-id`, and the `ARRAffinity` cookie, publishing:

- `dataversepool.http.distinct_frontends` (sliding-window distinct count)
- `dataversepool.http.ratelimit_burst_remaining` (min over window)
- `dataversepool.http.ratelimit_time_remaining`
- `server_request_id` as a log enrichment

Attribution to a pool member is only possible on controlled paths, via `x-ms-client-request-id`
correlation; document that raw-lease calls are per-host only. Flag experimental: the
`HttpRequestOut.Stop` payload is a legacy contract and the header semantics are undocumented.

### 5. WCF `IEndpointBehavior` injection via reflection
*Medium-high cost · unsupported*

The most precise option — per-clone, both `Headers` and `HttpResponseMessage`, covers every SOAP-path
read — but requires one internal property and breaks silently on SDK changes. If pursued:
feature-flag it, version-guard it, and back it with a live test that fails loudly when the member
disappears.

### 6. Not possible without X

A supported, public, per-call response-header hook on `Execute`/CRUD does not exist in 1.2.27.
ADR-0008 stands on that point. Update ADR-0008 / ADR-0016 / ADR-0024 to record
`RecommendedDegreesOfParallelism`, the request builder, the WCF and `DiagnosticListener` routes, and
the SOAP-path detector gap — so the next reader doesn't repeat the same incomplete survey.
