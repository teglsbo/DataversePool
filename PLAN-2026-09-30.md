## Phase 2: Throttle detector (the blocking item, 1–2 days plus live time)

**Blocked on observing a SOAP throttle, not on credentials:** the ignored local `.env` now has
two application users' credentials. Real single-user `CreateAsync` bursts of 100, 200 and 300
completed with zero rejections, despite 100/200/300 locally outstanding calls respectively;
local concurrency does not prove that many requests were simultaneously active at the server.
The probe now records exception types, SOAP fault codes and `ErrorDetails` key/type shapes if a
rejection occurs, and verifies cleanup. Do not implement SOAP detection from inference alone.
An additional read-only burst of 150 parallel `RetrieveAllEntitiesRequest(Entity)` calls through
pooled SDK/SOAP clients took about 123s; all 150 succeeded, with no throttle fault. By contrast,
the existing pinned raw-Web-API slow-search test issued 128 calls and saw 100 HTTP 200 responses
and 28 HTTP 429 responses (`Retry-After` 6m07s–7m45s). The controlled HTTP result confirms
server-side throttling can still be triggered; it does not establish SOAP fault shape. The local
ignored `.env` has an extra assignment on its URL line; test-process URL extraction must remove
that suffix until the file is corrected.

An in-process HTTP probe confirmed that `HttpHandlerDiagnosticListener` does not observe the
SOAP warm-up (zero events on a successful request), whereas `System.Net.Http` `EventSource`
does. In one 150-call metadata burst, the EventSource saw 299 host-matched starts and 299
activity-paired completions, peak 150 outstanding HTTP events, zero observed 429s, and a
~138-second spread between first and last HTTP starts; all 150 SDK calls succeeded. Activity
IDs are shared by concurrent calls (151 overlapping-ID starts), so completions are paired
FIFO by ID rather than exactly correlated to an individual request. `RequestStop` lacks host
information, so its status counts could include traffic to other hosts sharing an ID; do not
interpret the peak as server execution concurrency or the ~2:1 event/call ratio as proof of
retries. No SOAP throttle signature was obtained. A transport-level trace with unambiguous
request correlation, or a controlled proxy, is needed to distinguish extra HTTP requests,
queuing, and retries.

**Confirmed live, 2026-10-02:** `ConcurrencyBurst_WithRealWrites_ProducesGenuine429s` (150 real
`CreateAsync` calls against member A) produced 63 genuine rejections, 87 successes. Every
rejection was `System.ServiceModel.FaultException<Microsoft.Xrm.Sdk.OrganizationServiceFault>`
with `ErrorCode = -2147015898` (`ConcurrentRequests`) and an `ErrorDetails["Retry-After"]` entry
holding a boxed `TimeSpan`, observed ranging ~5 to ~13 minutes in that run. No
`NumberOfRequests`/`ExecutionTime` fault was observed live (only inferred from documentation);
the detector below still matches all three documented codes defensively. This is a SOAP fault,
not an HTTP 429 - confirming the gap step 1 asked about: `DataverseThrottleDetector` previously
only recognized `HttpOperationException`/429 (the Web API path) and silently missed every one of
these 63 real SOAP throttles (they fell through to the test's `OtherException` bucket).

- **`NumberOfRequests` (`-2147015902`) confirmed live.** 10 concurrent `WhoAmIRequest` calls for
  ~2 minutes (26,067 attempts, ~209 req/s, peak in-flight 10) produced 13,532 genuine
  `NumberOfRequests` rejections - the detector's SOAP-fault matching (Phase 2, step 2) correctly
  recognized these too, with `Retry-After` ranging 47ms up to the 80s cap. All three documented
  fault codes are now live-confirmed on this tenant, not just inferred.
- **`ExecutionTime` (`-2147015903`) not reproduced, even well past the documented budget.** 10
  concurrent `RetrieveAllEntitiesRequest(Entity)` calls for 4 minutes accrued 2,421,454 ms of
  cumulative client-observed busy time (2x the documented 1,200,000 ms/300s budget) with zero
  throttles; a repeat at 20 concurrent for the full 300s window accrued 6,111,426 ms (5x the
  budget) - still zero throttles. Either this tenant's execution-time budget is materially higher
  than the documented default (plausible - its concurrency ceiling is also custom, 100/40 vs. the
  52 default), or server-side "execution time" tracks well below full client-observed call
  duration (the open caveat in the research doc's §2.2, now with live evidence pointing toward
  it: at a 5x-over-budget client-duration sum with zero rejections, a literal 1:1 tracking
  assumption looks increasingly unlikely on this tenant). Not re-attempted at higher load in this
  session; env vars `DVPOOL_IT_EXECTIME_WORKERS`/`DVPOOL_IT_EXECTIME_SECONDS` exist to push
  further if useful.

**Follow-up, 2026-10-02 (continued): batched `ExecuteMultiple`, still not reproduced.** Per
Microsoft's own guidance that large batches inside a single `ExecuteMultipleRequest` shift
pressure from request-count onto execution-time (research doc §2.1), added
`Sustained_WithBatchedExecuteMultipleCreates_TriesToTripTheExecutionTimeLimit`: 4 concurrent
workers (well under the concurrency ceiling), each sending 200-record `CreateRequest` batches in
a single `ExecuteMultipleRequest` call, sustained for 3 minutes. Result: 124 batches, 24,800
items, all 24,800 succeeded, 732,566 ms of cumulative client-observed busy time (61% of the
1,200,000 ms/300s budget) - zero throttles of any kind. This is the third distinct attempt
(sustained heavy reads at 2x and 5x budget, now large-batch writes at 0.6x budget) to trip
`ExecutionTime` on this tenant; none have succeeded. Combined with the custom (higher than
default) concurrency ceiling already observed on this tenant, the working hypothesis is that this
tenant's execution-time budget is also configured above the documented default, rather than that
execution-time tracking is fundamentally different from client-observed duration - though that
caveat (research doc §2.2) remains open. `DVPOOL_IT_EXECMULTI_WORKERS`/`_BATCH_SIZE`/`_SECONDS`
exist to push further (larger batches and/or longer runs) if useful. Cleanup of probe records is
opt-in only (`DVPOOL_IT_EXECMULTI_CLEANUP=1`); by default records are left in the tenant, tagged
`DataversePool-IT-<runTag>` in their `subject`, since one-by-one deletion of thousands of records
was previously far slower than the load phase itself (now batched via `ExecuteMultiple`
`DeleteRequest`s when enabled). This run left 24,800 such task records in the tenant, tagged
`DataversePool-IT-6a77763b81124bc0a7ea21f58db21592`.
